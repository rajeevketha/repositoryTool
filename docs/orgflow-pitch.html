OrgFlow · Internal use
Context

Small configuration changes still consume disproportionate time

Administrators typically complete a field, layout, or flow in a sandbox in well under an hour. Moving that work to QA or production often takes much longer than building it.

Handoffs

Promotion frequently waits on someone fluent in VS Code, change sets, or a release tool. The delay is process, not complexity.

Fragmented tooling

Workbench, the Salesforce CLI, and enterprise DevOps platforms each solve a different job. None is designed for a short, named configuration move.

Inconsistent packages

Rebuilding the component list in each environment increases the chance that QA and production do not receive the same change.

Recommendation

Adopt OrgFlow for administrator-led promotions

OrgFlow is a Chrome extension. Staff select the configuration they built, retrieve a snapshot from the source organization, and deploy that same snapshot to the target organization.

What this provides

  • A guided source-to-target path in the existing browser
  • No Salesforce CLI, DX project, or Connected App
  • Optional team repository later; not required to start
  • No incremental platform license to evaluate first

What this is not

  • Not a replacement for VS Code or engineering CI
  • Not a substitute for Copado, Gearset, or Flosum
  • Not a data-migration or full-org compare product
  • Not an automated dependency analyzer

Fit

Intended users

Appropriate

  • Salesforce administrators and configurators working primarily in Setup
  • Promotions of a defined set of named metadata (fields, layouts, flows, permission sets)
  • Teams that want a shared history later, not as a prerequisite
  • A time-boxed pilot before any platform discussion

Not appropriate

  • Apex, Lightning Web Components, and continuous integration
  • Multi-stream release trains and formal environment governance programs
  • Record or data movement between organizations
  • Discovery of unknown dependencies across an entire org

Operating model

Four sequential steps; later steps stay closed until the prior one is complete

1. Start

Sign in to the source and target Salesforce organizations in Chrome. Detect sessions. Select From and To. The two organizations must be different.

2. Package

Review recent changes in the source organization and select the components to move. OrgFlow assembles the package; staff do not author XML.

3. Retrieve

Retrieve a snapshot from the source. Jira is optional when storing on the device, and required if a shared repository is enabled.

4. Confirm

Review the path and contents. Run a validation (dry run) if required. Deploy. The same snapshot can be promoted to the next environment.

Comparison

Change sets and enterprise DevOps platforms

Change sets

Effective for occasional, well-known components. Slow to assemble, easy to omit a related item, and inconvenient to reuse across QA and production. OrgFlow keeps a single named list and a single snapshot.

Copado, Gearset, Flosum

Appropriate for multi-team release trains, compliance, and broad org comparison. Disproportionate for a two-item configuration move. OrgFlow is intended to sit beside those platforms, not displace them.

Repository-only process

A Git repository without a selection interface still requires a developer. OrgFlow can write versioned snapshots to GitHub, GitLab, or Azure DevOps after the administrator has selected the components.

Deliberate limits

OrgFlow does not migrate records, compare entire organizations, or infer dependencies. Staff promote what they selected. That constraint is a control, not an omission to close in this product.

Governance

Access, blast radius, and audit

Access

Uses the Salesforce session already present in Chrome. No Connected App. Optional Git credentials remain in that browser profile and are not written to the repository.

Blast radius

Only named metadata is deployed. Source and target cannot be the same organization. Validation is available as a dry run. Apex tests may be executed in production if policy requires coverage.

Audit

Device storage: local snapshots; Jira optional. Shared repository: Jira key and comment required; versions reside in the team warehouse under a known folder structure.

Proposal

A two-week pilot

Scope

  • Two administrators; two sandbox or disposable organizations
  • One representative change (for example a field and layout, or a flow)
  • Promote source → QA using device storage
  • Optional: connect a test repository in the second week

Success criteria

  • A complete promotion without developer assistance
  • The target organization receives the selected components
  • No new platform license required to complete the pilot
  • A clear decision on whether a shared repository is needed
OrgFlow · Internal use
Decision

Requested action

Approve a two-week pilot with two administrators. Defer any discussion of replacing existing DevOps tooling until that pilot has a written outcome.

Distribution

Chrome Web Store listing, or load the unpacked extension from the internal zip. Two signed-in Salesforce organizations are required. Source and target must be different.
